## What was delivered

### 1. `src/rpg/pro.js` — the unlock module (new, no dependencies)

- `mintProCode(payload)` — mints a redeemable code for an 8-hex payload
  (`PG-<payload>-<checksum>`). Used by the seller (Ko-fi) and by tests; ships no
  list of valid codes.
- `isValidProCode(code)` — local validation only: normalizes case/dashes/spaces,
  checks the shape, recomputes the checksum, compares. No network, no account.
- `restorePro(profile, code)` — **the "Restore Pro" entry point.** Returns the
  profile with `pro: true` on a valid code, `null` on an invalid one (profile
  untouched), and is idempotent on an already-Pro profile.
- `hasPro(profile)` — reads the flag.
- Checksum: first 8 hex chars of `HMAC-SHA256(key, "pokergym:pro:" + payload)`.
  SHA-256 + HMAC-SHA256 are implemented in-file (~70 lines) and verified against
  the FIPS 180-4 / RFC 4231 vectors in the test.

**Key note (deliberate, documented in the module header):** the checksum key is
bundled with the client and is *not* a secret. There are no server secrets by
task bounds; offline validation means the key ships. It is a "pepper" that stops
typos and casual guessing, not DRM. Anyone reading the client source can mint a
code. That is accepted for this checksum gate; real entitlement enforcement is a
later server decision if ever wanted.

### 2. `src/rpg/state.js` — Pro flag on the save (survives export/import)

- `createProfile` now sets `pro: false`.
- `sanitizeProfile` (the allowlist that rebuilds a live profile from storage or
  an imported backup) now carries `pro: profile.pro === true`, so the flag
  survives `serialize`/`deserialize` and `sanitizeProfile`, and any non-boolean
  `pro` is coerced to `false`.

### 3. `src/rpg/backup.js` — strict import validation

- `readBackup` now rejects any backup whose `pro` is present but not a boolean,
  matching the existing strict-field style. Legacy backups with no `pro` field
  remain valid (they normalize to `false`).

### 4. `test/pro.test.js` — unit tests (new)

Covers exactly the requested cases:
- **valid code** → `restorePro` sets `pro: true`;
- **invalid code** → returns `null`, profile byte-identical;
- **flag survives export/import** → `writeBackup`/`readBackup`, `sanitizeProfile`,
  and `serialize`/`deserialize` all preserve `pro: true`;
- **no change to any free feature** → valid unlock changes only the `pro` field;
  fresh profiles carry `pro: false` and no gameplay field is affected;
- plus checksum-primitive vectors (SHA-256 `"abc"`, HMAC-SHA256 RFC 4231 case 2).

## Deferred: the `/web/` UI wiring (for Claude, after Nov 13)

The only remaining piece is the user-facing control. Exact wiring, ready to apply:

In `web/app.js`:
```js
import { restorePro, hasPro } from '../src/rpg/pro.js';
// after the existing backup/restore handlers:
function applyProCode() {
  if (!profile) return;
  const restored = restorePro(profile, el('proCodeInput').value);
  if (!restored) { el('proStatus').textContent = 'That code is not valid. Nothing changed.'; return; }
  profile = restored; save();
  el('proStatus').textContent = 'Gym Pro unlocked. It travels with your save and backup.';
}
el('btnRestorePro').onclick = applyProCode;
```

In `web/index.html`, a small input + button next to the existing backup control,
plus a line showing the current Pro state (`hasPro(profile) ? 'Gym Pro' : 'Free'`).

`restorePro` already enforces the exact semantics above (returns `null` on an
invalid code and never mutates the profile), so the UI wiring is the only thing
left and it cannot weaken any free feature.
